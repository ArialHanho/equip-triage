# v0.3: 30,000개 합성 장비 세션

이 연구는 최초 36 세션 결과를 확장한 **AI 작성 참고 구현**이다. 최초 결과는 smoke test로만 남기고 여기의 데이터·학습·평가는 별도로 실행했다. 외부 사전학습 모델·가중치를 사용·다운로드하지 않는다. PyTorch 라이브러리만 쓰며 전체 모델은 무작위 초기화한다.

## 데이터와 분할

seed 42, 30,000개 개별 seed의 합성 세션을 실제 생성했다. 원본 업무 로그나 회사 자료를 사용하지 않는다. 각 세션은 별도 난수 추출이지만 같은 수작업 생성기를 공유하므로, 30,000개가 독립적인 실제 장비/공정 분포를 대표한다는 뜻은 아니다. family는 30개뿐이며 검증·테스트의 독립 family 수는 각 3개다.

| 분할 | 세션 | 이벤트 행 | 정상 | 이상 | family / 가상 장비 / 조건 |
|---|---:|---:|---:|---:|---|
| 학습 | 24,000 | 608,178 | 24,000 | 0 | 24 / 240 / 120 |
| 검증 | 3,000 | 77,601 | 2,850 | 150 | 3 / 30 / 15 |
| 테스트 | 3,000 | 80,511 | 2,850 | 150 | 3 / 30 / 15 |

합계 **766,290행**. 평가 이상율 5%는 실공정에서 추정한 수치가 아닌 시뮬레이션 가정이다. 낮은 이상율 환경을 위한 최초 가정이며 실제 운영 빈도·비용을 입증하지 않는다. 평가에는 잘못된 조건부 release, unload 누락, 순번 누락, 과도 지연, 중복 순번, 시계 역행 6종을 넣었다. 정상에는 측정 반복 수, 합법적인 WAIT, 단계별 CHECK 위치, 간격 jitter를 바꿨다. 앞서 읽은 MODE_A/B를 여러 단계 뒤 release까지 기억해야 한다.

family는 5단계의 고유 CHECK 패턴으로 정의한다. family·장비·조건 ID를 split 사이에 격리하고, STEP 경계 토큰으로 family별 패턴이 구분되도록 했다. 시간 간격 조건 범위도 split마다 다르다. 단순 ID 분리만으로 격리를 주장하지 않는다. 완전한 수치 이벤트 payload 중복 **0**, split 간 이벤트 ID 시퀀스 중복 **0**을 검사했다. 같은 split 안의 이벤트 ID만 보면 추가 중복 **559개**가 있으며 숨기지 않고 결과에 집계했다. 시각을 제거하면 정상 패턴이 반복되므로 세션 수를 완전히 다른 문법 수로 해석하지 않는다. 레이블/장비/조건 ID는 모델 입력에 넣지 않는다.

## 모델과 평가 계약

- 정상 train만 학습한다. seed 42, CPU 1 thread, batch 128, 3 epochs 고정. 테스트로 epoch나 임계값을 선택하지 않았다.
- 9,389개 파라미터 한 블록 Transformer는 Q/K/V, 다중 head, scaled dot-product, causal mask, sinusoidal 위치, residual을 참고 코드에서 직접 구성한다. 목표는 한 칸 이동하며 target=-100 패딩은 손실에서 제외한다. 미래 이벤트를 보지 않는다.
- trigram은 같은 학습 세션에서 이전 2개 이벤트와 backoff/add-one smoothing을 사용한다.
- 상태기계는 앞의 MODE를 기억하고 정상 LOAD/측정/UNLOAD/release/END 문법을 검사하는 강한 기준선이다. 생성기 문법을 알고 있어 의도적으로 유리하다. 자동 학습 모델의 실세계 우위와 비교하는 근거가 아니다.
- 이벤트 ID 전용 방법과, 시간/순번 규칙을 공통으로 더한 방법을 별도로 보고한다. 수치 입력이 없는 모델이 시간/순번 이상을 놓치는 것은 한계다. 정상 간격은 알려진 조건 interval로 정규화한다. 3배 초과 지연과 비연속 순번·역행을 공통 규칙으로 표시한다.
- 점수는 관측한 각 이벤트의 surprise 최댓값이다. 매 시점에는 그때까지의 입력만 참조한다. 여기의 지표는 완료된 세션의 요약이며 온라인 경보 지연 성능이 아니다.
- PR-AUC는 같은 점수를 묶어서 계산한 step-integrated **average precision(AP)** 이다. 평가 이상율 5%에서 무정보 AP 기준은 0.05다.
- 운영 임계값은 검증 **정상** 세션 점수의 99% 분위수, 판정은 엄격한 `score > threshold`. 검증 오경보율 ≤1%를 목표로 고정하고 테스트에 그대로 적용한다. 테스트 오경보율을 다시 1%로 맞추지 않는다.

## 실제 CPU 결과

[results-30k.json](results-30k.json)에 전체 집계·임계값·유형별 재현율·실행 조건을 남겼다. PyTorch 2.9.1+cpu, seed 42, 3 epochs. 한 머신에서 학습 약 9초였으며 시간은 환경별로 다르다.

| 방법 | 테스트 AP | 테스트 재현율 | 검증 오경보율 | 테스트 오경보율 |
|---|---:|---:|---:|---:|
| trigram, 이벤트만 | 0.2924 | 0.2533 | 0.0000 | 0.0000 |
| Transformer, 이벤트만 | 0.5063 | 0.4667 | 0.0098 | 0.0344 |
| trigram + 공통 수치 규칙 | 0.8315 | 0.8200 | 0.0000 | 0.0000 |
| Transformer + 공통 수치 규칙 | 1.0000 | 1.0000 | 0.0098 | 0.0344 |
| 모드 기억 상태기계 + 수치 규칙 | 1.0000 | 1.0000 | 0.0000 | 0.0000 |

생성기의 문법을 아는 상태기계가 가장 좋은 운영점을 보였다. Transformer는 trigram이 놓친 조건부 release를 찾았지만 검증에서 0.98%였던 오경보가 테스트에서 **3.44%**로 증가했다. AP가 높아도 고정 운영점이 일반화된다는 뜻은 아니다. 이 데이터에서 복잡한 모델이 강한 규칙보다 낫다고 말할 수 없다. 이상 주입은 정상 문법과 뚜렷이 분리되는 편이고 실제 계측 노이즈·미등록 정상 문법·공정 전환을 충분히 모사하지 않는다.

## 재현과 Colab

저장소 루트, Python 3.12:

```sh
python -m venv .venv
# Linux/macOS: source .venv/bin/activate
# Windows: .venv\Scripts\activate
python -m pip install torch==2.9.1 --index-url https://download.pytorch.org/whl/cpu
python research/v03/scale_pilot.py --seed 42 --epochs 3 --out results-local.json --export-jsonl sessions-local.jsonl
python -m unittest discover -s research/v03 -p test_scale.py -v
```

생성 JSONL은 약 39MB이므로 저장소에는 넣지 않고 생성 코드와 집계 결과를 제공한다. 가중치는 파일로 저장하지 않는다. 재현 시 만들어지는 데이터는 합성 전용이다. [self-contained Colab 노트북](../../notebooks/equip-triage-v03-30k.ipynb)은 외부 소스 파일 없이 30,000개 생성부터 실제 학습까지 실행한다. 노트북 코드 셀 순차 실행은 클라우드 CPU에서 검증했다. Colab 웹 UI에서의 실제 실행 검증은 별도로 구분한다.

## 남은 검증

모든 수치는 한 seed의 최초 합성 실험이다. 여러 seed, 더 많은 독립 family, 새로운 비공개 생성 규칙, 시계 jitter/순번 재시작/정상 장기 지연, 실제 허가된 익명 데이터 및 운영 비용 검증이 남았다. 공개 테스트를 본 후 변경한 모델에는 새 블라인드 테스트가 필요하다. 현재 모델은 앱·장비·생산망에 연결하지 않았다. [직접 기여 범위](../../CONTRIBUTIONS.md)를 따른다.
